# ADR-0001 — Fetch evidence at build time; keep no database

**Status:** accepted · 2026-08-02

## Context

Hallmark's claim is that its evidence is not self-reported. That claim is only as strong as the
path the data takes from source to page. Three options:

1. **Curated data file** — a `builders.json` committed to the repo.
2. **Database** — ingest to Postgres/Firestore, serve from there, let builders claim and edit
   their own profile.
3. **Fetch at build/ISR time** — derive everything from the GitHub API on each regeneration,
   store nothing.

## Decision

Option 3. Every fact rendered is fetched from GitHub at build time and again every 30 minutes.
There is no database and no write path anywhere in the application.

## Rejected, and why

**Curated data file** is the fastest to build and the most common choice in this field — and it
quietly destroys the product. The moment a human types a peer's production URL into a JSON file,
the site is asserting a claim on that peer's behalf, which is the exact failure Hallmark exists
to remove. It would also be stale within hours on a deadline day when submissions are still
merging.

**A database with builder-editable profiles** is the richer product and several peers built it.
It was rejected because self-editing reintroduces self-reporting: a profile a builder can edit
is a profile a builder can inflate, and then the marks sit next to unverified prose with no
visual distinction between the two. It also adds auth, a write path, PII, and retention duties
(see `SAFETY.md`) for a site whose useful lifespan is one contest week.

## Consequences — what we gave up

- **Up to 30 minutes of staleness.** On a merge-deadline day this is real: a builder who merges
  at 16:58 may not appear until the next regeneration. Mitigated by rendering `checkedAt` on the
  page so a reader always knows the age of what they are looking at.
- **No builder-owned pages.** Builders cannot add context, correct a mis-parse, or link work
  that lives outside the PR body. The one-liner we quote is whatever they wrote in their
  submission — which is fair, but it is not their best copy.
- **Coupled to one API.** GitHub down means no fresh data (degradation path in
  `ARCHITECTURE.md` §Failure recovery).
- **Rate limits are now an architectural concern.** Unauthenticated GitHub allows 60 req/hr; a
  cold build makes roughly 100 calls. A read-only token is therefore mandatory, not optional.

## What would change our mind

If Hallmark outlived the contest and builders needed to correct genuine mis-parses, the answer
is **not** editable profiles — it is a builder-submitted correction that is itself verifiable
(e.g. a PR against this repo), so the provenance chain stays intact.
